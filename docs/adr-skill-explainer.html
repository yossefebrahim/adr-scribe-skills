adr-scribe · internal alpha

How the /adr skill works

A Claude Code skill that captures an architecture decision while the evidence is still in the conversation — then refuses to write anything it cannot attribute to you.

The one-sentence version. You type /adr. The agent reads the session you just had plus your working tree, decides whether a real architectural decision happened, classifies every claim by where the evidence came from, asks at most three questions, shows you the exact bytes it wants to write, and writes them only after you say yes — through a crash-safe transaction that never touches git.

Part 1

The cycle

Nine stages. Four of them can end the run without writing anything — that is the design, not a failure mode. "No ADR needed" is a normal outcome.

S0

Preflight

Confirms it is inside a git repository and that python3 ≥ 3.9 exists. Reads $ARGUMENTS — your optional hint, e.g. /adr we chose Riverpod over Bloc — and treats it as evidence only for what it literally says.

loads repository-states.md if unusual exit: not a git repo
S1

Evidence gathering — three sources, all read-only

1. The conversation you just had — the primary source, and the only place intent can come from. 2. The working tree — status, diffs, and bounded untracked files. 3. Existing ADRs — full bodies of any duplicate or conflict candidates, not just the index summary.

Never runs git fetch. Never copies raw transcript into the record. Untracked files are read only if they are in scope, under 128 KiB, text, not symlinks, and capped at 20 per run.

git read-only, hardened
S2

Significance test

A decision earns a record only if it selects or rejects a real architectural option and constrains more than one component, sets a rule others must follow, outlives one release, or is expensive to reverse. Renames, formatting, and routine bumps are excluded.

loads significance.md "No ADR needed" is a valid end
S3

Provenance classification — the heart of it

Every material claim is tagged with where it came from. Only two of the four classes may support intent. An agent's unacknowledged suggestion is not your decision; an implementation proves what was built, never why.

loads provenance.md
S4

Gap interview — at most three questions

Asked in one message, only for material gaps the evidence cannot fill. If your answers still don't support a claim, that claim is dropped — or the whole record is cancelled. Ambiguity never becomes architectural law.

cancelled — insufficient evidence
S5

Sensitive-data check

Scans the proposed bytes for credentials and customer data. Anything found is redacted, and anything remaining needs its own specific confirmation — separate from the write approval.

S6

The exact-patch preview

The agent runs prepare-record, which produces the final bytes — digest computed, index rendered, approver named. You see exactly what will land. Then one question: "Approve this exact patch for writing?"

Anything other than yes is not approval. Any change means a new preview.

loads madr-format.md runs prepare-record declined → nothing written
S7

Apply

apply-record takes the approved digest and performs the write transaction in Part 4. It writes documentation only — it cannot stage, commit, push, or fetch.

runs apply-recordloads transaction.md on failure
S8

Report

Every candidate decision gets exactly one outcome — written, not significant, cancelled, declined, or failed — so a run that quietly did nothing can't hide.

Part 2

How the agent loads it

A skill is not a plugin and not a running process. It is a folder of Markdown and scripts that the agent reads progressively — three tiers, each paid for only when needed.

The scripts are never "loaded" in the context sense. The agent doesn't read apply-record into its context window and reason about it — it runs it as a subprocess and reads the JSON that comes back. That is the whole point: the parts that must be exactly right are code, not prose the model has to remember.

Two things this skill deliberately does not do

It does not fork

Skills can run in a forked sub-context. This one must not. A forked skill cannot see the conversation whose provenance it exists to capture — it would be reconstructing intent from the code, which is exactly the failure it's built to prevent.

It does not pre-approve tools

The frontmatter could list allowed-tools to skip permission prompts. It doesn't. Tool permission is not human approval, and conflating the two would quietly dissolve the one gate that matters.

Part 4

The write transaction

Between your "yes" and the file existing, eleven steps run. The awkward truth they're designed around: creating a file and replacing another cannot be made atomic together on a portable filesystem — so instead of pretending, the protocol makes every intermediate state recoverable. 

 1  verify root      git rev-parse --show-toplevel → open(O_DIRECTORY|O_NOFOLLOW)
 2  resolve targets  component-by-component openat(O_NOFOLLOW) → any symlink ⇒ refuse
 3  acquire lock     mkdir(".adr-scribe.lock")  ← atomic; already exists ⇒ staleness check
 4  record owner     pid + process start token + timestamp → fsync
 5  journal          phase="prepared" + expected sha256 of EVERY output → fsync
 6  re-check         preconditions still hold? changed ⇒ stop, nothing written
 7  stage            render outputs inside the lock dir (same filesystem) → fsync
 7a bootstrap        create docs/ and docs/adr/ if missing → fsync parent
 8  create ADRs      linkat(tmp→dest) — atomic and fails if the target exists
 9  replace index    re-read + hash-match → save preimage → renameat → fsync
10  verify           re-read bytes, validate schema, check index membership
11  complete         journal → rename lock to .adr-scribe-completed-<ULID> → remove
Why the journal records hashes before writing anything. The phase label always lags the operation — there is a window where the file exists but the journal still says "prepared". Recovery therefore identifies state by hash, never by phase: a file whose bytes match the expected hash can only be ours, so it is safe to adopt and continue. A recovery routine that trusted the phase label would be unable to recover the most likely crash windows.
What it will never do. Overwrite a file it didn't just create · follow a symlink · write outside the repository root · execute a command it found in your repo · run git add, commit, push, or fetch · claim success after a failed verification.

Part 5

The limit worth knowing

One guarantee is weaker than it looks, and saying so is part of the design.

The same model both renders the preview and calls the writer with the approved digest. The writer can prove its input matches the digest it was handed — but not that a human ever saw those bytes. In principle a model could display one thing and apply another.

So "never writes unapproved bytes" is a procedural guarantee under an honest model, not a mechanically enforced one. Closing it properly needs something Claude Code doesn't offer today: an approval receipt issued by the host and bound to the writer's digest. Until then the practical mitigation is unglamorous — the writer echoes the digest and every destination path, and you git diff before committing.

What is deliberately not built. The behavioural evals — does the significance rubric actually fire correctly, does provenance classification hold up — need labelled fixtures drawn from your real sessions. Those are the Phase-0 kill gate, and they are the one part of this that cannot be written on your behalf.

That roughly halves the largest remaining milestone, but it changes what the PRD requires, so it is yours to decide.
